# Working in this repository

This repository is public. Keep real prospect data, hostnames and credentials out of code, tests, commits and PRs; fixtures use invented people on `.example` domains.

## Commands that touch shared state

Several sessions may be working on this machine at once. These are the commands that can collide:

- **`prospector serve`** listens on `127.0.0.1:8766`, or `:$PORT` when `PORT` is set. Check the port is free first, pass an explicit address (`prospector serve 127.0.0.1:<port>`), and stop the server when done.
- **`DATABASE_URL`** is required, a `postgres://` URL; the app runs on Postgres only. For a throwaway run, point it at a database of your own on your own Postgres (see the tests below), never at 5432.
- **The tests run on Postgres.** `go test ./...` needs `PROSPECTOR_TEST_PG` to point at a server it may create databases on; without it the run stops and prints a `docker run` for a throwaway one. Port 5432 on this machine is another project's: start your own on a spare loopback port, with `-c fsync=off -c synchronous_commit=off -c full_page_writes=off`, which more than halves the run. Each run makes databases named `prospector_test_<random>…` from the database the URL names and drops them when it ends, so runs from several sessions can share one server; it never touches that database's own tables.

Tests call `t.Parallel()` and get a database from `tempStore(t)` (one migrated template, copied once per parallel slot and emptied between tests) or, to change the schema, `freshDatabase(t)`. A test that sets the environment or swaps a package variable stays serial.

## Before a change is done

- It passes the linters CI runs: in `web/`, `npm run lint` (oxlint, with the rules of React), `npm run format:check` (oxfmt; `npm run format` fixes it) and `npm run lint:api` (Spectral on `api/openapi.yaml`); at the root, `golangci-lint run ./...` (v2, `.golangci.yml`: go vet, staticcheck, errcheck and the rest, with gofmt and goimports). A rule broken on purpose gets a disable comment on the line saying why.

- Every page a person sees is React; the server renders no HTML of its own.
- The public site (the front page and the `/api` reference) is React in `web/src/site/`, rendered to HTML when the app is built (`web/prerender.mjs` writes `assets/app/site.html` and `api.html`), so it reads without script. The front page's script (`site.js`) only adds the enquiry form, and the server leaves it out where there is no form. The reference is laid out from `web/src/site/apidoc.json`, which Go writes from the spec (`apidoc_view.go`): after changing `api/openapi.yaml`, run `PROSPECTOR_WRITE_APIDOC=1 go test -run TestTheAPIReferenceIsBuiltFromTheSpec .` (with `PROSPECTOR_TEST_PG` set, as for any test) before building `web/`. When a feature makes the front page wrong or deserves a mention, change `web/src/site/Landing.tsx` in the same PR. The site is built from the app's shadcn components, wrapped for its look in `web/src/components/app/site.tsx`, and styled by the shared `assets/css/output.css` (rebuild it after adding classes).
- The built web app (`assets/app/`, `assets/js/`) is not committed: goreleaser, the Dockerfile and CI build it, and the binary embeds it. Run `npm ci && npm run build` in `web/` before `go test` or `prospector serve`, and again after changing the spec or anything in `web/`; `serve` refuses to start without it. Commit the `web/src/api.d.ts` it regenerates; CI fails if that differs.
- The app inside an organisation is a React front end in `web/`; Go serves its shell and the API. Every page at `/o/{org}/<page>` (and `/o/{org}/companies/{id}`, `/o/{org}/tasks/{id}`) gets the same `assets/app/index.html`, built by Vite from `web/index.html`, under the usual sign-in, policy and headers; the pages are listed in `appPages` in `app_ui.go`, with the agreements prepare page at `/o/{org}/agreements/{id}/prepare`. The old `/o/{org}/app/…` addresses redirect to the real ones. The front end:
  - routes with TanStack Router in `web/src/router.tsx`: one route constant per page (inline in `addChildren` they lose their types), path ids parsed to numbers, and every search param a zod schema in `web/src/search.ts`, with real types (numbers as numbers, enums for filters) and a bad value falling back to the default through `.catch`. Pages read them with `useSearch`/`useParams({ from: "/o/$org/…" })` and link with typed `Link`s; a page the server serves must be routed there too (a test checks);
  - draws the sidebar itself (`web/src/components/app/layout.tsx`) from `GET /o/{org}/api/v1/nav`, which also gives the pages `useSession()`;
  - reads and writes only through the typed client (`$api` in `web/src/client.ts`, openapi-react-query over the spec). Anything it needs that the API lacks goes into `api/openapi.yaml` first;
  - builds from shadcn/ui. `web/src/components/ui/` is exactly what `npx shadcn@latest add <name>` writes (run it in `web/`): never edit those files. Prospector's look goes in wrappers in `web/src/components/app/`;
  - draws while its data loads, and nothing already on screen moves when it arrives (`web/src/components/app/skeleton.tsx`). A row, card or heading is one component with its data optional, showing a `Bar` one line tall in place of each piece of text; a list shows `placeholders` rows of it; a query whose filters or page change keeps its previous data (`keepPreviousData`, never on a query for one entity); a block whose presence or size depends on data and sits above others is held back, or the parts stacked under it go in `Settled`; placeholders stop when a load fails. Each page is its own chunk (the `pages` table in `router.tsx`), named for its content;
  - takes its styles from the shared `assets/css/output.css`, so rebuild the CSS after adding classes;
  - is built with `npm run build` in `web/`, which writes `assets/app/index.html` and `assets/app/main.js` (not committed).

  Go tests of what a page shows assert on the API, since the shell is the same at every address.
- A page with no API to ask, because it is an error or is for someone outside the organisation (starting a first organisation, a customer's onboarding at `/c`, an unsubscribe link at `/u/…`), is the same shell with what the server decided in `<div id="app" data-page="…">` (`writeShell` in `app_ui.go`, read by `web/src/served.ts`). The app draws it in place of any route. Its forms are plain `<form method="post">`s to the server's own `/c/…` and `/u/…` routes, which answer with the next page. Put in the payload only what the page shows: a customer's step says whether they marked it, never which member did. Go tests read it back with `served(t, body)`.
- The API is spec-first. Change `api/openapi.yaml`, run `go generate ./api`, and commit the regenerated `api/api.gen.go`; CI fails if they differ. A page or form does what it does through the API, never through a route of its own, and each operation names the key scope it needs. Each operation also lists every error status it can answer with, as the shared `components/responses` (no `default`), and every error is a Problem (RFC 9457). A refusal a client acts on without reading `detail` gets a `ProblemType` (`/api/problems/<name>`, with a line in its `x-enum-descriptions`), and is written with `typed{…}` or `writeTyped`. The test binary checks every answer the suite sees against the spec and fails if an operation answered with a status it doesn't declare. The server's only other routes are the signed-out ones (sign-in, reset, `/c/…` and `/u/…`), `POST /password`, and the enquiry intake.
- Every word a person sees or hears goes through react-intl: `defineMessages`/`useIntl`/`<FormattedMessage>` in components, `intl` from `web/src/i18n.ts` outside them, and dates, times and numbers through `intl.formatDate`/`formatNumber` (`web/src/lib/format.ts`), never `toLocale…` with a fixed locale. Each message has a `description` for the translator, and an id that is a hash of its text: write a message without one and `npm run lint -- --fix` fills it in (and changes it when the English changes, so the translations ask again). Counts and joined phrases are ICU messages (`{n, plural, one {# lead} other {# leads}}`), not `plural()` or string concatenation. `npm run build` gathers them into the committed `web/lang/en-GB.json` (the source; `web/locales.json` lists the languages) and fails a translation whose keys or placeholders differ. `eslint-plugin-formatjs`, run by oxlint, fails on English in JSX or in the props people read (`aria-*`, `title`, `label`, `hint`, `placeholder`, `alt`…) outside the files listed in `.oxlintrc.json`'s override, which are still to be translated: take a file off that list when you translate it, and add one only for a branch begun before this rule (and say so in its PR). It doesn't see English in plain strings outside JSX, so sweep those by hand. Open the app or the sign-in page with `?lang=en-XA` to see untranslated text stand out; the choice is kept in a cookie for every page after, and `?lang=` forgets it.
- `assets/css/output.css` is a committed Tailwind build. A utility class that isn't already in it renders unstyled until the CSS is rebuilt (`node build-css.mjs <node_modules with tailwindcss v4>`), so prefer classes already in use.
- Pages are served under a Content-Security-Policy that allows only the app's own scripts: no inline `<script>`, no `on…=` attributes. `TestContentPolicy` checks every page.
- A behaviour change ships with a test in the top-level `*_test.go` files.
- Code outside the store reaches the database through exported `Store` methods that take their organisation first, which `TestNoMethodReachesIntoAnotherOrganisation` tries as another one; a sweep over every organisation, or a lookup by a secret token, is named in its `acrossOrganisations`. A method handed a row takes the organisation too, and filters and writes by it, not by the row's `OrgID`. `TestOnlyTheStoreTouchesTheDatabase` fails on `.db`, `.in(` or any unexported `Store` method used outside a `Store` method, and on an unexported `Store` method sharing its name with another type's. A method that only acts on rows in a state the fuzzing can't guess (a run held by a named server, a mail still queued) goes in `saysNothingBack` and into `TestRunsAndMailsStayInTheirOrganisation`.
- A new table that holds an organisation's data, or points at a contact, has to be carried by the exports, erasure and restore. `tables_test.go` fails until it is, or until it says why not.
- A column added to a model reaches existing databases through auto-migration on start-up. Give it a not-null default and test it against a table that already has rows.

## Merging is releasing

`main` only takes pull requests, and the `test` and `vulncheck` checks must pass. Every green push to `main` is tagged as the next patch version and published as a release, which `deploy.yml` then installs on the host its `DEPLOY_*` secrets name. Treat a merge as a deploy. To go back, run the `deploy` workflow by hand with an earlier version.
